Grounding Context

Codebase Context

  • Thinkroom — open-source, agent-native collaborative workspace. Ruby 3.4 / Rails 8.1, React 19 + TypeScript via Inertia. Real-time editing: Yjs (y-prosemirror, Milkdown) over Action Cable with server-side y-rb 0.7.0 (yrs Rust bindings). Storage is SQLite in dev and prod; Kamal deploys are pinned to WEB_CONCURRENCY=1 because SQLite and Solid Cable share one volume.
  • Write path (app/services/yjs_persistence.rb): per frame — base64 decode → per-document in-process Mutex → document.with_lock + reload → build a fresh Y::Doc from the full stored blob → sync(update) → re-encode full_diff → rewrite the whole yjs_state blob. O(document) work per keystroke frame.
  • Read/join path: state_b64 rebuilds a fresh Y::Doc per subscribe and ships full state + state vector; the same bytes already rode the page as the yjs_state_b64 Inertia prop (instant paint), so a page load ships the document 2–3×.
  • Dual model: yjs_state blob is sync truth; client-pushed content_markdown/provenance_spans + server-rendered content_html are the agent/read-API projection. content_generation guards stale-CRDT resurrection after owner CLI replace_content!.
  • Ordering workaround: SyncChannel keeps a per-subscription client seq + gap buffer (MAX_SEQUENCE_GAP=256) because y-rb's full_diff silently drops unresolved pending structs — out-of-order persistence would lose edits on reload.
  • Standing findings: two validated-but-unfixed P2s (corrupt blob bricks every subscribe — load_ydoc has no rescue; cable frames unbounded vs 2 MB HTTP caps), a P3 (LOCKS map never evicted), zero logging/metrics in the persistence service, and no SQLite backup tooling at all.

Past Learnings

  • Team optimized correctness first: per-frame sequencing, generation guards, snapshot state-vector gates. No documented learnings on compaction, update logs, or perf benchmarks — greenfield territory.
  • Failed approaches: the y-rb_actioncable gem (message loss, per-subscription doc memory); broadcast-only invalidation; updated_at-based staleness. Planned but never shipped: a 500 ms debounced single-writer merge.
  • Invariants any idea must keep: merge stays the authorization + generation + lock boundary; broadcast only after durable persist; dual-model separation stays; document.with_lock stays (only cross-process guard); no server-side Yjs structure authoring; content_generation (not timestamps) signals resets; protocol changes need gradual rollout compatibility.

External Context

  • Universal consensus across production Yjs backends: don't rewrite the full blob per update — append incremental updates, compact periodically. Yjs updates are commutative and idempotent, so appends need no ordering coordination.
  • yrs-kvstore (official, same Rust core as y-rb): per-doc keyspace {snapshot, state vector, sequenced updates}, periodic flush_doc. Hocuspocus: in-memory doc while clients connected, debounced store, flush on last disconnect. y-redis: stateless servers, stream per doc, separate compaction workers. Automerge repo: lock-free compaction — write new snapshot, delete only incorporated chunks; trigger when incremental bytes exceed snapshot size.
  • Kevin Jahns: blob-only update merging skips GC — a 50 KB doc ballooning to 20 MB is documented; yjs#710 shows naive mergeUpdates blowup (divide-and-conquer fixes it). yrs core exposes merge_updates_v1 / diff_updates_v1, but the verifier confirmed y-rb 0.7.0 exposes none of them and only accepts Array<Integer> — update-level APIs require a gem fork/upstream PR.
  • Verifier also confirmed by running the installed gem: y-rb hardcodes yrs defaults, so GC already runs on every fresh-doc rebuild — the current path is not accumulating tombstones (that hazard only appears if a blob-only merge path is adopted).

#1

Append-only update log + snapshot compaction

Storage format & compaction Confidence 85% Complexity High
Description
Change the durable act of YjsPersistence.merge from "rewrite the whole blob" to "INSERT the raw update bytes" into a yjs_updates table (document id, seq, payload, and — as a cheap rider — sender + generation + byte size for a transport-level audit trail). The merge boundary keeps its mutex, with_lock, writability, and generation checks; broadcast still fires only after the durable append. A compactor folds the log into the yjs_state snapshot by loading a real Y::Doc (yrs default GC runs there), writing the new snapshot, and deleting only the rows it incorporated — Automerge's lock-free rule — with an explicit policy for orphaned pending updates (rows whose causal dependency never arrived are retained and surfaced, not silently dropped). Triggers: log bytes exceed snapshot bytes, idle/last-disconnect, and a forced snapshot on content_generation bump. Once landed, the per-subscription seq/gap buffer becomes deletable: out-of-order arrival is harmless when raw updates are stored and merged as a full set.
Basis
direct: every non-no-op frame executes document.update_columns(yjs_state: ydoc.full_diff.pack("C*"), ...) after load_ydoc rebuilds a fresh doc from the whole blob (app/services/yjs_persistence.rb); the original editor plan specified a 500 ms debounce that never shipped. external: yrs-kvstore (same Rust core) persists exactly this shape — snapshot + sequenced update keys + periodic flush_doc; Hocuspocus, y-redis, y-partykit, and Automerge all converge on append-then-compact. Verifier verdict: sound.
Rationale
Today one keystroke costs O(document): decode blob, Rust-merge, re-encode, rewrite the SQLite row — inside the app's only write path, under two locks. The append log caps per-frame work and SQLite write amplification at the size of the edit, which is the single biggest lever on typing latency at scale — and it deletes ~40 lines of sequencing machinery (including the MAX_SEQUENCE_GAP silent-drop data-loss vector) instead of hardening it. SQLite's WAL mode makes appends the cheap operation on this exact substrate.
Downsides
A schema migration and a new compaction subsystem with its own failure modes (orphan policy, crash-during-compaction). Reads must merge snapshot + tail until compaction runs. The no-op/seed_state guard needs rework. Rollout must keep seq-accepting behavior until old clients age out.
#2

Instrument the persistence hot path first

Resilience & hardening Confidence 95% Complexity Low
Description
Wrap merge, state_b64, and persist_snapshot in ActiveSupport::Notifications events carrying duration, lock-wait time, update bytes, blob bytes before/after, and rejection kind (stale generation, gap drop, snapshot-gate refusal, decode failure). Stop persist_snapshot from swallowing decode errors as indistinguishable-from-staleness false. Export to logs or AppSignal and alert on merge-failure rate and blob-size p99.
Basis
direct: app/services/yjs_persistence.rb contains zero Rails.logger / ActiveSupport::Notifications / instrument calls (grep: no matches); persist_snapshot ends in rescue ArgumentError → false with no logging; the only pipeline signals are three Rails.logger.warn lines in the channel. Verifier verdict: sound.
Rationale
Every performance claim in this document — merge cost scales with doc size, bursts amplify writes, joins double-ship — is currently unmeasured, and every silent edit-loss mode (gap drops, stale rejections, swallowed decode failures) vanishes into a warn line or nothing. The measured thresholds are literally the compaction and debounce policy of ideas #1 and #4. This is the natural first PR: land instrumentation, collect dogfood data, then size everything else from real distributions.
Downsides
None material — small overhead per event; needs a decision on where metrics land (logs only vs AppSignal).
#3

Materialize the state vector and handshake at write time

Read/join path & handshake Confidence 90% Complexity Low
Description
Every subscribe currently calls state_b64, which rebuilds a fresh Y::Doc from the blob and re-encodes both full_diff and the state vector — immediately after a merge computed and discarded those exact values. Persist a yjs_state_vector column (and optionally a blob digest) inside the existing update_columns at merge time; subscribed then serves two stored byte columns with zero yrs instantiation. replace_content! nulls the sv alongside the blob. The stored sv is also the server-side half of any future differential handshake.
Basis
direct: state_b64 calls load_ydoc(document) then encodes full_diff + state per invocation (app/services/yjs_persistence.rb). external: yrs-kvstore stores the state vector as its own key precisely so reads skip doc instantiation. Verifier verdict: sound.
Rationale
Joins are the read path that scales with audience — every reload, reconnect, and late-joining reviewer, plus reconnect storms after each deploy where every client re-runs the handshake at once, at exactly the moment the server is busiest. This makes join cost O(bytes served) instead of O(document) CPU, is one column and independently shippable this week, and becomes strictly more valuable under ideas #1 and #7.
Downsides
One more column that must stay coherent with the blob (single write site makes this easy); full-state bytes are still shipped until a differential handshake exists.
#4

Resident per-document Y::Doc session cache

Write path / merge hot path Confidence 70% Complexity Medium
Description
Keep the merged Y::Doc in memory per document while subscriptions exist — the Hocuspocus model — evicting on last disconnect. Inside the existing mutex + with_lock, validate the cached doc against content_generation plus a blob digest after reload; on match, apply only the incoming update instead of rehydrating the whole blob; on mismatch (CLI replacement, cross-process write), fall back to the current full rebuild. The same registry finally gives the never-evicted LOCKS map an eviction lifecycle, with the standing rule that every per-document in-memory structure names its eviction trigger.
Basis
direct: load_ydoc builds Y::Doc.new and syncs the whole stored blob on every merge and every subscribe; the residual P3 notes the LOCKS map "grows one Mutex per document id, never evicted"; deploys are pinned WEB_CONCURRENCY: "1" so in-process coherence is already guaranteed. external: Hocuspocus and y-partykit hold the doc in memory while clients are connected. Verifier verdict: sound — and notes a resident doc is strictly better than today on the pending-struct hazard, since the current fresh-doc-per-merge path can silently drop cross-client dependent updates via full_diff while a resident doc retains pending structs until dependencies arrive.
Rationale
This captures most of idea #1's hot-path win — O(update) applies, no per-frame rehydration, subscribes served from the cached doc — with zero schema or protocol change, making it the credible incremental step if a new table is judged too invasive right now. Its invalidation story (generation + digest under with_lock) also defines exactly what multi-process would later require.
Downsides
Introduces authoritative in-memory state on the sync path (the thing the current design deliberately avoids); memory scales with concurrently-open docs; correctness depends on the single-process pin holding until the digest check is trusted. Team must decide whether this is a stepping stone to, or substitute for, idea #1.
#5

Self-healing durability stack

Resilience & hardening Confidence 85% Complexity Medium
Description
Three layers, each covering the failure the previous cannot. Prevent: round-trip-validate a newly encoded blob into a fresh Y::Doc before committing it, plus a checksum column — most corruption never lands. Contain: rescue in load_ydoc; on failure, quarantine the corrupt bytes to a side table (forensics, not deletion), fall back to the last-good retained snapshot, and let connected clients re-upload the missing tail via the sync-reply step that already exists in the protocol. Retain the last N generation-tagged snapshots and make replace_content! archive rather than null yjs_state — turning the product's most destructive operation into a reversible one. Recover: Litestream streaming replication of the SQLite file to off-host object storage, with a written and rehearsed restore procedure.
Basis
direct: validated P2 — "Corrupt stored yjs_state blob bricks every subscribe permanently" (docs/residual-review-findings/feat-proof-reimagining.md); load_ydoc confirmed rescue-free; replace_content! sets yjs_state: nil; grep for backup|litestream across the repo returns no matches. external: A/B firmware banks (validate before flipping, keep the old bank bootable). Verifier verdict: sound (all three components individually verified).
Rationale
The CRDT blobs are the one unreconstructable dataset in the product — snapshots and HTML are lossy derivations — and today they live as a single SQLite file on a single volume with a known permanent-outage failure mode and no backups. For a product whose strategy is provenance and trust, "put this document back" must be answerable before the first incident, not after. The plain P2 fix shape (degrade to empty doc) silently loses all content when no client happens to be connected; last-good fallback bounds the loss to at most one update.
Downsides
Round-trip validation adds CPU per blob write (cheap if writes are debounced/compacted per ideas #1/#4); snapshot retention adds storage; Litestream adds an ops dependency and (modest) hosting cost.
#6

Durable client outbox — close the reconnect drop window

Read/join path & handshake Confidence 80% Complexity Medium
Description
Local Yjs updates made while !synced are dropped by handleDocUpdate and only re-sent at the next handshake — the documented user-visible bug being: accept a tracked edit, refresh before the handshake, and the edit reappears. The recovery machinery already exists: persistCurrentState sends Y.encodeStateAsUpdate(doc, serverStateVector) over a keepalive HTTP request into the same generation-guarded merge path. Extend it from checkbox toggles to a generic pagehide/visibilitychange flush of any pending diff (generation-stamped, under the ~64 KiB keepalive cap), optionally backed by a localStorage outbox keyed by (document, generation) for crash recovery.
Basis
direct: "CableProvider.handleDocUpdate drops local updates while !synced… the tracked edit reappears" (docs/plans/2026-06-07-001-fix-resolve-persistence-plan.md); the diff-vs-server-vector keepalive path exists at app/frontend/editor/cable_provider.ts and lands in the generation-guarded sync_update endpoint. Verifier verdict: sound — the plan explicitly deferred the offline story as "its own feature," which is what this proposes.
Rationale
This is the one grounded entry describing a user-visible lost edit in a shipped feature, and the fix is mostly composition of existing pieces rather than new protocol. The generation stamp means a stale tab flushing after a CLI replacement cannot violate the resurrection guard. Storage-side ideas cannot close this gap alone — reconnect durability is a client-and-server contract.
Downsides
Keepalive body cap bounds what a single flush can carry (large pending diffs need the outbox path); localStorage outbox needs eviction and privacy consideration on shared machines.
#7

Stateless durable-relay endgame

Concurrency & multi-process scaling Confidence 60% Complexity High
Description
The horizon design idea #1's road leads to: the server never materializes a Y::Doc on any hot path. Writes run the authorization + generation checks (row fields, checkable under with_lock) and append; joins serve the last compacted snapshot plus the raw tail rows, and the client applies them — Yjs clients handle out-of-order application natively via their own pending-struct resolution. yrs runs only in the background compactor. Appends are coordination-free (updates commute), so the persistence layer stops being a reason for the WEB_CONCURRENCY=1 pin — remaining constraints (Solid Cable polling, shared volume) become the explicit blockers to lift.
Basis
direct: the in-process lock exists precisely because "two concurrent receives could both read the same stored blob and the later write would drop the earlier update" (app/services/yjs_persistence.rb) — a read-modify-write hazard append-only writes do not have. external: y-redis (stateless servers, stream per doc, worker compaction) is this architecture in production; k_yrs_go compacts at read time past 100 rows. Verifier verdict: sound, with one named wrinkle — the no-op/seed_state guard needs rework.
Rationale
This converts correctness-by-topology (single process, in-process mutex) into correctness-by-format, which is what actually unlocks horizontal scaling — and it reframes the seq/gap machinery and per-frame merges as symptoms of one architectural choice rather than necessary complexity. It is deliberately ranked as the endgame, not the next step: land #2, #3, then #1 first; each stage is independently valuable and reversible.
Downsides
The server loses the ability to render current state synchronously (snapshot may lag the log); largest blast radius of any idea here; only worth it when measured load or multi-node requirements justify it.
Sequencing note

The survivors form a verified roadmap, not seven competing bets: #2 (instrument) → #3 (materialize sv) → #1 (append log, absorbing the seq-buffer deletion) → #7 (stateless relay), with #4 as the no-schema-change alternative fork after #3, and #5 / #6 schedulable independently at any point. Each stage is independently shippable and makes the next one cheaper.
